# External-involvement classification rule and incremental-refresh procedure

This document defines how a Premium Blend Netflix Managed Services queue request is labelled as "external involvement" on the SLA dashboard, and the exact procedure for keeping that labelling current as new requests arrive. It is the single source of truth for every run, whether a person or an agent performs it. It was written on 2026-10-29, immediately after the first full classification of the 286 Slack intake threads, the 10 Gmail-reactivation orphan tasks, and the 34 Sprinklr request-form cases.

## What the dashboard measures and why the label exists

The Queue SLA tab reports three medians for the Premium Blend request queue: acknowledgement (arrival to first pickup), first response (arrival to first human reply), and completion (arrival to fulfilment). The external-involvement label splits that queue into two mutually exclusive subsets so the dashboard can show both the Overall SLA across every request and the SLA restricted to the requests that required a team outside Premium Blend. The purpose is to make visible how much of the queue's completion time is spent waiting on other teams, which the first production run quantified as a completion median of eleven days against four hours for the requests Premium Blend resolved alone.

## The operational definition

A request is classified EXTERNAL when a Premium Blend person escalated it to a team outside Premium Blend in order to resolve it. Three escalation paths each qualify as external, and each was observed in the source threads. The first path is a Sprinklr support ticket, recognisable from language such as "raised to support", "raised with Sprinklr", "Support confirmed", "via support", "Sprinklr Support was able to reproduce", or any variant of the verb "escalate" directed at Sprinklr. The second path is a page to the Netflix MarTech or MarData on-call through the `!oncall martech-mardata-support` command in the intake channel, which routes to the Netflix engineers Piyush Khalya, Thanya Begum, Sherry Yang, and Ann Kettles. The third path is a consultation with Sprinklr product or engineering, including cases where a Premium Blend person loops a named Sprinklr engineer such as Joel Kretzinger into the thread or the email.

A request is classified INTERNAL when Premium Blend resolved it directly, without escalating to any outside team. The internal set is dominated by five recurring request types that Premium Blend handles end to end: reactivating a deactivated Sprinklr account, granting or adjusting dashboard access and permissions, making a configuration change, fixing a naming-convention or taxonomy or tagging error, and explaining how to use a dashboard or how a metric is computed. A request that was answered, configured, reactivated, or tagged by a Premium Blend person with no handoff to an outside team is internal even when the underlying question concerned Sprinklr behaviour.

A request that has not yet been read and labelled is UNCLASSIFIED. The dashboard shows it as its own bucket and never counts it as internal, because treating an unread request as internal would understate external involvement. The classification maps are a point-in-time snapshot, so every request that arrives after the snapshot date is unclassified until the maps are regenerated.

## The detector pitfalls that force a human or model read

A literal keyword search cannot perform this classification correctly, which is why each thread must be read and judged. Four concrete failure cases establish the point. A closing pleasantry such as "feel free to raise a new request in the channel" contains both "raise" and the channel context yet signals no escalation, so a naive "raise" plus "support" rule produces a false positive. A sign-off that directs the requester to "reach out to sprinklr-support" names the support alias without any escalation having occurred, another false positive. A genuine escalation can carry no clean keyword at all, as in "Sprinklr support has indicated it's resolved", which a keyword rule misses as a false negative. A requester who describes their own role, as in "I am on the games product team", is not evidence of external involvement, because the test is whether Premium Blend escalated outward, not whether an outside team is mentioned. These cases are the reason the classification step requires reading the actual conversation rather than matching strings.

## Where the labels live and how the pipeline applies them

Two committed files hold the classification. The file `external_map.json` at the repository root carries the Slack side, keyed three ways for every request so the pipeline resolves it regardless of which identifier a row presents: by the Slack thread timestamp, by the Slack message timestamp, and by the Asana task gid. The gid key exists because some requests, specifically the Gmail-inbound account reactivations named `[Reactivation]`, have no intake-sheet row and therefore no timestamp for the pipeline to look up; the pipeline falls back from the timestamp lookup to the gid lookup for exactly these rows. The file `sprinklr_external.json` at the repository root carries the Sprinklr side, keyed by the request-form `intakeResponseId` as a bare number string such as `706`, which matches the pipeline's `str(intakeResponseId)` with no `#` prefix. Each entry records the external boolean, the responsible team, and a short evidence string citing what was read.

The pipeline file `sla_refresh.py` loads both maps once at module import through `_load_ext_map`, which tolerates a missing or malformed file by returning an empty map rather than failing the run. For each row it sets `external_involved` to the boolean when the row's key is present in the map and to `null` when it is absent, and it sets `external_team` to the recorded team. After building the rows it prints one coverage line per source in the form `external coverage [Slack]: external 50, internal 257, unknown 0 (of 307)`, which is the post-deploy proof that every row resolved; an `unknown` count above zero names the number of requests that have arrived since the maps were last regenerated.

## The incremental-refresh procedure

Regenerating the maps does not require reclassifying the entire history. The procedure reads only the requests that are new since the last snapshot and appends them. The steps are the following enumerated sequence, performed in an environment that can reach Slack, Gmail, and the intake Google Sheet.

1. Read the current `external_map.json` and `sprinklr_external.json` and collect the set of keys already classified.
2. Read the intake Google Sheet "Requests" tab and the live Sprinklr request-form scrape, and compute the set of Slack thread timestamps, Asana gids, and Sprinklr `intakeResponseId` values that are present in the current queue but absent from the maps. These are the new, unclassified requests.
3. For each new Slack thread, read the full thread and apply the operational definition above to decide external or internal, recording the responsible team and a one-line evidence string.
4. For each new Gmail-inbound `[Reactivation]` task with no intake-sheet row, read the corresponding reactivation email thread and classify it, which in every case observed to date has been internal because Premium Blend performs the reactivation directly, with the single exception of a thread in which Premium Blend looped a Sprinklr engineer in for a follow-on configuration question.
5. For each new Sprinklr request-form case, classify it from its category and request text, since the Sprinklr scrape captures the form submission rather than a resolution thread.
6. Append the new entries to the two maps, preserving the three-way keying for Slack and the bare-number keying for Sprinklr, and open a pull request so the change is reviewed before it reaches the live dashboard.

## The environment constraint on automating this procedure

Step 3 and step 4 require reading Slack and Gmail, and step 2 requires reading the intake Google Sheet. A scheduled Claude Code cloud routine cannot use the Slack, Gmail, and Google Sheets MCP servers that this desktop session uses, because those servers are configured directly in Claude Code and are not attached to cloud routines. A cloud routine can perform the full procedure only when the account has Slack, Gmail, and Google Sheets connected as claude.ai connectors, which a routine can use. Absent those connectors, the procedure runs in a desktop Claude Code session that has the MCP servers, and a cloud routine can at most detect the count of new unclassified requests and signal that a classification run is due.
